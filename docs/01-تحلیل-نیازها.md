# مرحله ۱ — تحلیل نیازها (Requirements Analysis)

> نسخه ۱.۰ | تاریخ: ۱۴۰۵/۰۴/۰۶ | وضعیت: نهایی برای نسخه اول (MVP)

این سند پایه‌ی همه‌ی تصمیم‌های فنی است. هدف: یک نرم‌افزار **مدیریت مالی و فروش** برای کسب‌وکارهای کوچک که ابتدا برای **فروشگاه پوشاک** استفاده می‌شود ولی معماری آن برای همه‌ی کسب‌وکارهای کوچک قابل توسعه باشد.

---

## ۱. خلاصه محصول

| موضوع | توضیح |
|---|---|
| نام کاری پروژه | **حساب‌یار** (Hesabyar) — قابل تغییر |

## ۲. کاربران سیستم (Personas) و نقش‌ها (Roles)

در نسخه اول فقط یک کاربر (مالک) فعال است، اما ساختار نقش‌ها از همین حالا طراحی می‌شود تا آینده آماده باشد.

| نقش | کد نقش | دسترسی |
|---|---|---|
| مالک / مدیر | `owner` | دسترسی کامل به همه‌چیز، تنظیمات، گزارش‌های مالی |
| مدیر شعبه | `manager` | مدیریت یک شعبه، فروش، خرید، انبار، گزارش شعبه |
| فروشنده | `cashier` | فقط فروش، مشاهده محصول، مشتری |
| انباردار | `inventory` | ورود/خروج کالا، شمارش، انتقال |
| حسابدار | `accountant` | مالی، دریافت/پرداخت، گزارش‌ها |

> در نسخه اول فقط `owner` فعال می‌شود؛ بقیه نقش‌ها در دیتابیس تعریف می‌شوند ولی UI آن‌ها بعداً ساخته می‌شود.

## ۳. ماژول‌های نسخه اول (MVP)

### ۳.۱ داشبورد مدیریتی
- فروش امروز (مبلغ + تعداد فاکتور)
- فروش ماهانه
- مجموع هزینه‌ها (امروز/ماه)
- سود تقریبی (فروش − قیمت تمام‌شده − هزینه)
- ارزش موجودی انبار
- لیست کالاهای کم‌موجود (زیر حد آستانه)
- نمودار فروش ۳۰ روز اخیر
- خلاصه مانده صندوق و بانک
- خلاصه بدهی مشتریان / طلب تامین‌کنندگان

### ۳.۲ کالا و انبار
- **محصول:** نام، دسته‌بندی، برند، قیمت خرید، قیمت فروش، تصویر، حد کم‌موجودی
- **تنوع (Variant):** رنگ + سایز + کد کالا (SKU) + بارکد + موجودی هر تنوع
- **عملیات انبار:** ورود، خروج، تعدیل (شمارش)، انتقال بین شعبه‌ها، حواله، درخواست کالا
- **تاریخچه کامل تغییرات موجودی** (هر حرکت ثبت می‌شود — قابل ردیابی)

### ۳.۳ خرید
- تامین‌کننده، فاکتور خرید، اقلام خرید (با تنوع)
- هزینه‌های جانبی خرید (حمل، گمرک و...) با سرشکن‌کردن روی قیمت تمام‌شده
- افزایش خودکار موجودی پس از ثبت فاکتور خرید
- پرداخت نقد/کارت/نسیه به تامین‌کننده

### ۳.۴ فروش
- فاکتور فروش با اقلام (انتخاب تنوع)
- مشتری (اختیاری برای فروش نقدی)
- تخفیف (مبلغی یا درصدی، در سطح قلم و کل فاکتور)
- روش پرداخت: نقد، کارت، نسیه (یا ترکیبی)
- چاپ فاکتور (A4 و رسید حرارتی ۸۰mm)
- آماده برای اتصال بارکدخوان (ورودی کیبوردی) و POS
- کاهش خودکار موجودی پس از ثبت

### ۳.۵ اشخاص (Contacts)
- ساختار مشترک با نوع: مشتری / تامین‌کننده / هر دو
- نام، شماره تماس، آدرس، توضیحات، مانده حساب (محاسباتی)
- آماده برای CRM آینده (فیلدهای اضافی، تگ، یادداشت، تاریخچه)

### ۳.۶ مالی (حسابداری مدیریتی)
- ثبت هزینه روزانه با دسته‌بندی
- دریافت (از مشتری) و پرداخت (به تامین‌کننده یا بابت هزینه)
- صندوق (نقد) و حساب‌های بانکی (چند حساب)
- انتقال بین صندوق و بانک
- محاسبه سود/زیان ساده

## ۴. خارج از محدوده نسخه اول (ولی دیتابیس آماده باشد)
- CRM کامل (کمپین، باشگاه مشتریان، پیامک، وفاداری)
- حسابداری رسمی (دفتر کل، سند حسابداری دوطرفه، اظهارنامه)
- AI Analytics (پیش‌بینی فروش، پیشنهاد سفارش)
- چند شعبه‌ای فعال (multi-branch) — ساختار آماده، UI بعداً
- چند کاربر همزمان با نقش‌های مختلف — ساختار آماده

## ۶. تصمیم‌های کلیدی طراحی (که در دیتابیس اعمال شده)

1. **همه جداول** دارای: `id`, `created_at`, `updated_at`, `created_by`, `branch_id`, `org_id`.
2. **org_id (سازمان):** برای اینکه در آینده چند کسب‌وکار روی یک سیستم (SaaS) کار کنند. هر کسب‌وکار = یک سازمان.
3. **مبالغ پول** به‌صورت عدد صحیح (`bigint`) و به واحد **ریال یا کوچک‌ترین واحد** ذخیره می‌شوند تا خطای اعشار نداشته باشیم. (نمایش به تومان).
4. **موجودی** هرگز مستقیم ویرایش نمی‌شود؛ همیشه از طریق «حرکت انبار» (stock_movement) تغییر می‌کند تا قابل ردیابی باشد.
5. **مانده حساب اشخاص و صندوق/بانک** از روی تراکنش‌ها محاسبه می‌شود (منبع حقیقت = تراکنش‌ها).
6. **حذف نرم (Soft Delete):** فیلد `is_active`/`deleted_at` به‌جای حذف فیزیکی، برای حفظ تاریخچه.

---

## ۷. پرسش‌هایی که باید تأیید کنید (روی این‌ها فرض پیش‌فرض گذاشته‌ام)
1. واحد پول: **تومان** (پیش‌فرض). ✔
2. آیا الان فقط یک شعبه دارید؟ فرض: **بله، یک شعبه** (ولی ساختار چندشعبه آماده است). ✔
3. آیا برای فروش نقدی ثبت مشتری اجباری باشد؟ فرض: **خیر، اختیاری**. ✔
4. مالیات بر ارزش افزوده: فرض فعلاً **غیرفعال** (فیلد آماده است). ✔

> اگر هر کدام از فرض‌ها فرق دارد، در پیام بعدی بگو تا اصلاح کنم.
